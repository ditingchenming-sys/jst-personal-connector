# 查询使用指引

本文面向已安装连接器的使用者，列出实际调用中容易出错的参数语义、字段含义和排查路径。
不涉及任何公司的内部编码习惯或业务数据；示例仅说明字段结构。

## 三个商品标识不要混用

聚水潭的商品有三层标识，查询参数不同：

| 标识 | 字段 | 说明 |
|---|---|---|
| 款式编码 | `i_id` | 一个款式下的所有颜色/尺码共用此编码 |
| 商品编码 | `sku_id` | 款式编码 + 颜色尺码后缀，最细粒度 |
| 商家编码 | `skuSn` | 商家自定义的唯一标识，各家定义不同 |

另有 `other_1` ~ `other_5` 一类**自定义字段位**，由商家自行决定放什么：
可能放内部款号、条码、批次，也可能留空。同一字段在不同公司含义不同，
用前请先确认本公司在这些字段里实际放了什么。

对应到 `query_erp` 的 Q02：

- `style_ids` — 按款式编码（`i_id`）筛选，传列表
- `unique_code` — 按 `other_1` 的值精确筛选，传单个字符串
- `include_related` — 展开 `other_1` 相同的其他款式，用于找出共用同一 `other_1` 的关联款

`style_ids` 与 `unique_code` 互斥，必须且只能提供其一，否则报 `INVALID_PARAMETERS`。
用错标识符**不会报错，只会返回空数组**，容易误判为"没有这件商品"。

`include_related` 要求首次查询结果完整（`complete: true`），
否则报 `PAGINATION_INCOMPLETE`——此时应先加大 `max_pages` 重查。

## Q02 不返回库存字段

Q02 固定只返回五列：`i_id` / `sku_id` / `other_1` / `properties_value` / `brand`。

需要库存或进销存数据时，通过商品接口自行取数：接口地址为
`https://apiweb.erp321.com/webapi/ItemApi/ItemSku/GetPageListV2`，查询体中
`queryFlds` 需显式列出需要的字段。两个硬性要求：

- **不传 `queryFlds` 返回空数组**（不是返回全部字段）
- `queryFlds` 中**不能包含无效字段名**，一旦混入无效字段，整条查询无结果

商品接口可取的库存相关字段：

| 字段 | 含义 |
|---|---|
| `qty` | 实际库存 |
| `order_lock` | 订单占有数（未发货订单占用） |
| `virtual_qty` | 虚拟库存 |
| `purchase_qty` | 采购在途 |
| `in_qty` | 入库数量 |
| `return_qty` | 退货在途 |
| `pick_lock` | 拣货锁定 |
| `orderable` | 可用数 = 实际库存 + 虚拟库存 − 订单占有 |

`orderable` 为负表示已被订单超卖，这是判断缺货风险的直接指标。
连接器不对这些字段做跨公司统一解释，各公司口径可能不同。

## 财务接口的必需参数

Q09 供应商清算、Q10 应付单、Q11 付款单都调用 `api.erp321.com/fms/api`。
直接调用底层接口时注意：

- 分页参数必须放在 `page` 对象里：
  `{"currentPage": N, "pageSize": 100, "pageAction": 0}`
  —— 缺失会报 `Value cannot be null`
- 返回结构是 `data = {fields: [字段字典], data: [数据行]}`，数据行在 `data.data`
- Q09 按款式编码过滤时用 `iIds`（对应返回行的 `skuIId`）。
  `skuIIds` / `skuIds` 不是有效参数，传了不会过滤而是返回全部

Q09 清算行包含单据、数量、金额、仓库与结算信息，常用字段：

| 分类 | 字段 |
|---|---|
| 单据 | `poId` 采购单号、`ioId` 入库单号、`inoutType` 单据类型、`ioDate` 入库日期、`poDate` 采购日期 |
| 商品 | `skuSn` 商家编码、`skuId` 商品编码、`skuIId` 款式编码、`name` 商品名称、`brand` 品牌、`propertiesValue` 颜色及规格 |
| 数量金额 | `qty` 入库数量、`remainQty` 剩余数量、`currencyPrice` 单价、`costAmount` 入库金额、`writeOffAmount` 已核销金额、`remainCostAmount` 剩余金额 |
| 仓库 | `whName` 仓库、`wmsName` 仓储方 |
| 结算 | `purchaserUserName` 采购员、`financeAuditStatus` 财审状态、`agingDays` 账期天数、`remark` 备注 |

Q10 应付单表头的 `remark` 字段常带有可检索的业务信息（如采购单号、款号、数量、金额），
是按业务维度反查单据的可行入口。全库规模随使用量增长，扫描时注意分页完整性。

## 只读端点是严格白名单

连接器只允许访问源码核对过的端点，按**完整 URL 全等**匹配（含 query）。
手工拼路径一律被拒：

```
该请求不在已审核只读端点中，已阻断
```

静态资源同样被拦。因此新增取数能力必须走
[通用探索与接口复用](通用探索与接口复用.md) 流程，由实际捕获的请求形成契约，
不能靠猜路径。

## 老式回调协议已不可用

部分页面（采购单、订单列表）历史上通过 `__CALLBACKID` + `__CALLBACKPARAM`
回调协议取数，聚水潭已将该协议下线，服务端返回：

```
ErrorCode:120009 系统功能已升级[{page}:LoadDataToJSON]，请刷新页面后继续操作
```

连接器会把它归类为 `ERP_SESSION_REJECTED`，提示"请核对本人登录与查看权限"——
**该提示指向登录，但实际问题通常不是登录或权限**。原始响应中 `GotoLogin` 为
`false` 时即属此情形，反复重新登录无效，需要改走通用探索重新对接。

## 完整性判断

每次查询都要检查返回中的 `complete` / `has_more` / `total` / `pages_read`：

- `complete: true` — 结果完整
- `complete: false` — 达到 `max_pages` 上限仍未读完，**不能当作全量结果**
- 总数在读取期间变化会报 `PAGINATION_INVALID`

查询失败会抛出错误码，**不会静默返回空**。返回空数组时应先排查参数：
标识符用错、`queryFlds` 未传或含无效字段、`iIds` 传错，都表现为空结果。

## 环境自检

```bash
# 登录与身份状态
jst-connector status --client <客户端名>

# 组件自检（密钥、浏览器、依赖）
jst-connector doctor

# 能力目录
jst-connector catalog --client <客户端名>
```

Windows 下 `jst-connector` 位于安装目录的 `.venv\Scripts\`，
Linux 下为 `.venv/bin/`。

## 通用探索的常见阻碍

| 现象 | 原因 |
|---|---|
| 探索编号无效 | 探索会话绑定浏览器上下文，跨进程会失效 |
| 静态抓取页面得不到业务请求 | 页面由前端框架渲染，需先交互触发 |
| 读不到前端脚本正文 | 探索缓存只保存脚本摘要与哈希，不保存正文 |
| 首页菜单接口 fetch 失败 | 探索环境会拦截部分请求，属预期行为 |

探查、交互、提案应在同一进程内连续完成。
